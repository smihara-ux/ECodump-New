## 集計定義

- 予定：取消・受入不可を除く対象日/場所/検索条件の便。実台数は車両IDで重複排除（未配車を除く）、延べ便数は1便単位。
- 実績：受入実績確定済みの便。差分：予定−実績の便。未着：未到着（遅延/締め時刻判定ではない）。取消は別明細。
- 原票確認済み数量：原票確認状態がconfirmedの実績だけ。確認待ち数量：提出されたpendingの数量だけ。t/m³を別集計し換算しない。
- 旧APIで確定した原票未照合実績は削除しないが、原票確認済み数量へ含めない。未確認伝票に含め、詳細で旧方式と明記。既存APIの互換経路は残るが、原票提出済みの場合の旧API確定はDB側で拒否。
- 滞在時間：人が照合済みの入場1件・退場1件で、退場≧入場の時だけ。片側なし、重複未解消、逆順は未確定。

## 保存と権限

新規マイグレーションはreceiving_evidence、guards、metadata。並行作業のdriver_documentsとresultを保存し、ドライバー原票入力項目を現在版の原票に関連付けて参照。
- 受入担当：既存 `direct.has_scope(location,'receiving')` のみ。配車権限は追加しない。
- ドライバー：割当運行の提出/差戻し再提出のみ。確認・訂正は拒否。
- 施工側：取引実績と提出書類の参照。受入確認は拒否。
- 未照合入退場：担当受入場所のみ。紐付け後も取引単位。添付URLは認証必須・RLS・no-store。別取引の写真を入退場照合で付け替えて共有できない。
- 受入更新は既存operation journalを再利用。二重送信は操作IDで1回、expectedVersionで古い/競合更新を拒否。応答切断時は再送せず結果照会。原本のUPDATE/DELETE権限なし。

- `regression-api.txt`：既存直接運搬13テスト＋集計/滞在3テスト（16 passed）。既存の配車・複数便・RLS・共有実績を維持。

## 操作・引き継ぎ

1. `http://127.0.0.1:5199/?preview=app&role=receiving&page=transport` を開く。通常は匿名サンプル。保存操作は既存の「ログインして保存を利用」から検証アカウントで接続（秘密情報は公開資料に記載しない）。
2. 日付/受入場所/検索を指定し、現場名または集計を押す。車両を選び3タブへ。原票と入力値を照合し、差戻し理由または確認チェックを入力して保存。
3. 入退場はまず要確認で記録し、車番/写真/対象便を照合。ホーム下部キューで未登録・予定外・二重検知を確認。対象運行が未作成の記録は要確認のまま保持。
4. 原票は同じ運行の取引添付を使用。未照合ゲート写真の独立アップロードは未対応。カメラ取り込み契約と写真保管方式が決まった後に追加。
5. テスト再実行：`node --test app/server/tests/receiving-evidence.test.mjs`、`cd app && node scripts/test-receiving-evidence-ui.mjs`。isolated API6103とフロント5199を使用。fixture.jsonは当該実行で生成する匿名DBレコードを指す。
6. 次工程：容量定義・予約取消/期間変更の合意ルールを確定し、保存済み取消状態へ接続。現状の共通予約DBはrequested/confirmedのみで、取消集計は既存試作データと集計テストの確認まで。実機カメラ/OCR/GPS・遅延閾値・本番認証/保存先は別途設定・検証する。

未決事項への推奨：容量は物理容量・期間処理量・契約枠を別項目にする。受入済み分を予約から減算するかは契約ごとに定義する。滞在時間は今回のように詳細のみ（主一覧の密度を抑える）。原票の最終確認は現在の受入場所担当に限定し、拡張承認フローは責任者合意後にする。
