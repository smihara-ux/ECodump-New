# ECO DUMP 操作試験手順・簡易操作説明

2026-09-25版。対象はローカルの匿名データによる操作試験。実地試験・本番の開始承認ではない。判定と未対応事項は [REPORT.md](REPORT.md) を参照。

## 試験前の準備

1. 施工担当・受入担当・ドライバー・試験記録担当を決める。同じ人が兼任する場合もブラウザープロファイルを分け、各役割の別アカウントで入る。
2. 共通保存画面を使用する。現在稼働中の入口は以下。`?preview=app` 内の試作画面／旧SQLiteとはデータが異なる。
   - [施工側](http://127.0.0.1:5205/?data=isolated&role=construction&date=2045-09-26)
   - [受入側](http://127.0.0.1:5205/?data=isolated&role=receiving&date=2045-09-26)
   - [ドライバー](http://127.0.0.1:5205/?data=isolated&role=driver&date=2045-09-26)
3. 画面の検証用ログイン情報を利用する。生成済み認証情報は `app/server/.local/credentials.json` にあるが、共有資料や画像には転記しない。既存アカウント・本番情報を入力しない。
4. 新しい試験には未使用の日付と匿名名を決める。今回の2045-09-26の2便は完了済みで、再実行用の未処理データではない。
5. 現場・受入場所・車両・ドライバーの担当範囲、受入可能量、時間帯を確認する。数量はm³でそろえる。距離やGPSを推測して登録しない。

## 施工側の簡易操作

1. 「搬出予定・予約を作成」で許可された現場と受入場所、日付、時刻、土質、予定数量、直接取引の条件を入力し申請する。
2. 確認ダイアログで保存内容を確認する。保存・再取得完了を確認し、予約IDを記録する。申請は予約確定ではない。
3. 受入側が確定したら「詳細を確認」から車両・ドライバーを選び配車する。
4. 同じ車両の2往復目は別の予約として作成し、別運行IDと往復番号を確認する。既存便を書き換えて使い回さない。
5. 再取得して運行状況を確認し、受入確定後に「搬出実績」で予定・実績数量を確認する。
6. ログアウト・再ログインし、日付を選び同じ実績が残ることを確認する。

## 受入側の簡易操作

1. 対象日の予約一覧から詳細を開き、受入場所、土質、予定数量・単位、時刻、条件を確認する。
2. 条件に問題がない予約で「条件を確認して予約確定」を実行する。受入不可や変更が必要なら現在の操作試験を中断し、未対応事項として記録する。
3. 再取得して現場到着、出発、受入先到着、荷下ろし完了の報告を確認する。
4. 荷下ろし完了後、受入実績数量を入力する。予定と異なる場合は差異理由を記録し、「受入実績を確定」を実行する。
5. 「受入実績」で結果を確認し、施工側でも同じ値が見えることを照合する。確定後の訂正は現状未対応なので誤入力を確定しない。
6. ログアウト・再ログインして数量・単位・状態が残ることを確認する。

## ドライバーの簡易操作

1. 自分のアカウントで「今日の運行」を開き、対象日を選ぶ。自分に割り当てられた便だけが表示されることを確認する。
2. 時刻・現場・受入先・車両・往復番号を確認し、対象便を開く。
3. 順に「現場到着を報告」→「積込完了・出発を報告」→「受入先到着を報告」→「荷下ろし完了を報告」を操作する。実地運用に移る場合は停車中に操作する。
4. 各操作で保存結果を確認する。荷下ろし完了は受入実績確定ではない。
5. 「運行履歴」で便を確認する。2往復目は別便を選ぶ。マイページからログアウトし、再ログイン後も状態が保持されることを確認する。
6. 位置情報・プッシュ通知は、この試験では作動確認済みの機能として扱わない。

## 発生土マッチ経由の操作

1. 施工側または受入側の「発生土マッチ」で「自社の案件」から匿名案件を下書きし、公開範囲を確認して公開する。
2. 相手側の「探す」で地域・土質・数量・単位・期間を指定して検索し、詳細から事前相談する。
3. 「相談・条件調整」で条件を提示・改訂する。変更した条件には双方の再確認が必要。
4. 双方が同じ条件版に合意し、「成立済み」で合意内容を確認する。案件を編集した場合も合意時点の内容が残ることを確認する。
5. 合意から予約を申請する。ここでは予約確定・配車済みにはならない。以降は上記の受入確定→施工配車→ドライバー報告→実績確定へ進む。
6. 公開資料・相談相手だけの資料・社内資料をそれぞれ別ユーザーで確認する。社内資料を共有用としてアップロードしない。

## 障害・例外時の扱い

- 結果不明：同じ内容を新しい操作として再送しない。画面に残る操作IDで処理結果を照会し、保存済みなら再取得する。未処理を確認でき、画面が明示的な再送を許可した場合だけ同じ操作IDで再実行する。
- 409／古い版：最新を再取得し、別担当者の変更を確認してから判断する。古い画面で繰り返し押さない。
- 再取得失敗：保存そのものが失敗したとは限らない。成功と決めつけず、照会結果と再取得で確認する。
- 変更・取消・再配車・遅延・受入不可・確定後数量訂正：現在の共通DB画面では未対応。運用開始条件が満たされるまで実地試験を行わない。操作試験中は対象便の試験を止め、ID・時刻・期待状態・実際の状態・役割を記録する。旧SQLiteへの入力やDB直接編集で補完しない。
- 権限違反で閲覧できた場合：画面を閉じ、機密内容を拡散せず、対象IDと役割を担当者に伝えて試験を停止する。

## 再試験を行う開発担当者へ

既存起動プロセス・ポート・未コミット差分を確認してから操作する。他担当のDBを削除・再初期化しない。

- マイグレーション準備：`cd app && npm run db:setup:isolated`。既存の全登録マイグレーションとチェックサムを維持する。
- 共通API：`npm run dev:api:shared`（6103）。UI：`npm run dev -- --host 127.0.0.1 --port 5205 --strictPort`。既存の同一プロセスが動いていれば再起動不要。
- API回帰：`node --test server/tests/integration.test.mjs tests/shared-matching-api.test.mjs tests/receiving-mutation-journal.test.mjs`。
- 画面横断：未使用の同じ `QA_DATE=YYYY-MM-DD` で `node scripts/test-shared-matching-ui.mjs`、続けて `node scripts/test-cross-role-readiness.mjs`。先の試験が作った合意・予約を次が使用する。試験データは残る。証跡を退避してから再実行する。
- 旧SQLite回帰は別枠：`node --test tests/workflow-api.test.mjs tests/matching-api.test.mjs tests/trial-operation-api.test.mjs`。
- 実行日時、環境、ソース状態、役割、予約／便ID、期待値、結果、画像、ログ、修正と再試験結果を記録する。秘密情報は除外する。

## 本番導入前に必要な設定・確認

以下は未確認事項／推奨案。採用済み仕様として扱わない。

|領域|設定・判断と合格条件|
|---|---|
|業務例外|P1の6操作を共通API・DBへ実装。履歴と訂正理由、権限、予約枠、割当、通知先、状態遷移を確定して再試験|
|認証・権限|運用用認証基盤、会社・役割・現場／受入場所の担当範囲、複数事業の切替、退職・失効、セッション管理を設定。画面のrole指定で権限が増えないことを再検証|
|DB移行|対象DBの既存スキーマ・拡張・全マイグレーションの互換性をステージングで確認。RLS・最小権限・監査・ロールバック手順を検証|

|可用性|バックアップ取得だけでなく復元試験、監視・アラート、障害窓口、処理結果照会、同時利用・負荷試験を実施|
|添付資料|保管先、容量・種類、ウイルス検査、閲覧権限、保存期間、削除方針を決定し実接続で確認|

|GPS・Push・外部|採用機能、提供元、同意、権限拒否、配信失敗、代替手順を決め、実端末・実サービスで検証。現状の画面表示だけで合格にしない|
|業務ルール|単位、計量方法、差異許容、確定／訂正権限、運行時間と車両重複判定、予約枠、休業、取消期限を確定|

推奨する順序は、例外フロー統合→隔離環境で再検証→ステージング認証／DBと実機確認→限定した現場試験→本番判断。理由は、現場で通常発生する変更や通信断に対し、記録と復旧経路を先に整える必要があるため。
