## 操作する画面

- 受入側: http://127.0.0.1:5199/?preview=app&role=receiving&page=matching
- 施工側: http://127.0.0.1:5199/?preview=app&role=construction&page=matching
- 専用検証プレビュー: 同じパスをポート5205で使用。
- 検証ログイン: 施工側 `construction@sample.invalid`、受入側 `receiver@sample.invalid`。パスワードは **`app/server/.local/credentials.json`** 内のローカル生成値。公開資料・ソースに認証情報を転記しない。本番Supabaseのユーザー・パスワードは使用しない。
- 合意から作った予約は「共通DBの予約画面へ」で `?data=isolated&role=...&date=...` へ遷移。同じ検証セッションとPostgreSQLを使用する。受入側の予約確定、配車、運行、実績は既存の共通DB画面で扱う。

## 既存を活用したもの

ECO DUMPロゴ、施工・受入の切り替え、メニュー、配色、画面枠、既存PostgreSQLの会社・ユーザー・所属・担当範囲・現場・受入場所・予約、検証セッション認証、非所有者API接続、既存の予約・運行画面。

初期Supabase SQL・Authクライアントは存在するが、本番Supabase Auth/DBへ接続した検証ではない。今回のAPIは専用DB名・ローカル接続を検査し、検証セッションで本人を特定する。

## APIとデータ

同一実装 `app/server/index.mjs` の別ローカルリスナー6103を使用。6102で進行していた他担当の検証を停止せず、**同じ `ecodump_direct_validation` DBと認証テーブル**へ接続している。新しいDBや第三のバックエンドは作っていない。

- `POST /api/direct/session`: 既存の検証ログイン
- `GET /api/match/list?side=construction|receiving`: 公開検索・自社案件・相談・合意・担当場所・自社変更履歴
- `POST /api/match/actions/{create,edit,publish,close,consult,offer,accept,reserve}`: 全更新にUUIDのIdempotency-Key。編集・条件提示・同意には現在のversion
- `GET /api/match/operations/:key`: 認証本人の処理結果。未確認の場合は更新を再送しない
- `GET /api/match/documents/:caseId/:documentId`: 共有範囲を再検査してファイル内容を返す

`direct.match_cases` → `match_consultations` → `match_offers` → `match_acceptances` → `match_agreements` → 既存 `direct.bookings`。
`match_history` は案件版、`match_operations` は冪等結果を保持。予約を作るまで運行・配車・実績レコードは増えない。

APIの本人特定に加え、DB関数で担当範囲と操作権限を検査。マッチの生テーブルにはauthenticatedの直接SELECT/UPDATE権限を与えず、明示的なDB関数経由で共有列を限定する。ドライバーはマッチを利用できない。監査before_dataを通じてドライバーに条件メモが見える問題も、担当範囲に限定するポリシーで閉じている。

1. `20260925_matching.sql`: テーブル・認可付き関数・公開範囲
2. `20260925_matching_refinement.sql`: 相談メッセージ、合意時の資料本体、日時指定、テキスト検証、監査共有制限
