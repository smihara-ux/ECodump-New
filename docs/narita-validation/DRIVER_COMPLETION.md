# ドライバー画面・共通連携の仕上げ（2026-09-25）

## 担当境界と正本
共通 API/DB の変更は施工担当に集約する。受入担当との共通migrationファイル名重複を検出し、両担当へ連絡して編集責任を調整した。ドライバー側は `src/driver/` と `src/integration/ConnectedApp.jsx` のドライバー部分を変更する。DGX は変更しない。

共通 master ID は `app/server/setup.mjs` の `naritaIds`、管理場所は `COMMON_LOCATION.md`。画面専用の master/予約/便データは作らない。既存 PostgreSQL `ecodump_direct_validation`、検証アカウント認証を利用する。

## 着手時の分類
|分類|機能|
|---|---|
|完成済み・再利用|本人運行取得、4段階報告、写真＋手入力の原子的伝票提出、受入側差戻し・確認、原票、IndexedDB下書き、操作ID結果照会|
|修正必要|複数便を予約IDで識別してしまう表示、報告時刻と受信時刻の表示、古い割当の下書き再確認、画面内お知らせ、アカウント切替時の非同期取得競合|
|DB未接続（着手時）|外部運送会社、1予約複数便、代車代走、問題報告、運行訂正。共通担当が追加migrationで対応|
|仕様未確定|報告状態の巻戻し権限、実績確定後の運行訂正、容量の契約上の意味、GPS・外部ナビ・OCR・Push連携|

## 既存資料との差異
- `DRIVER_SCOPE.md` の「共通seed/ID待ち」は過去時点の記録。現在は `setup.mjs:naritaIds` に集約済み。
- 旧資料の1予約1便は複数便への移行対象。ドライバーUIは同じ予約IDが複数あっても `trip.id` で選択し、報告・伝票に明示的な `tripId` を付ける。
- 運行到着と入場、荷下ろしと退場・受入数量確定を引き続き分離する。予定数量を原票数量欄へ自動入力しない。

## 今回の画面修正
- 便ID・往復番号・車番・行先を表示。次の便と完了/取消便を分離。
- 配車の車両・担当・行先・時刻変更を検知した場合、内容確認まで報告・提出を停止。
- 伝票に `tripId` と取得時 `expectedTripVersion` を送信。API側の照合と併用する。
- お知らせに共通DB上の伝票確認待ち・差戻し・実績確定と、本人の端末未送信下書きを表示。Pushとは分離。
- 報告時刻とサーバー受信時刻を別々に表示。
- 通信切断表示、結果不明操作の保持、手動照会。自動再送なし。
- ログアウト/認証切れで表示を消去し、旧セッションの遅延レスポンスが新ユーザー画面に混入しないよう保護。

## 操作説明
1. [ドライバー確認URL](http://127.0.0.1:5202/?data=isolated&role=driver)で本人の検証アカウントを使用する。
2. 今日の運行で所属・車番・行先・便番号を確認し、次の便を開く。
3. 停車してから状態報告を順番に行う。入場・退場・受入実績は別の処理。
4. 担当が違う／遅延などは「問題報告・担当の確認依頼」で理由を入力し、確認ダイアログから送信する。
5. 伝票を撮影またはJPEG/PNGファイルで添付し、原票数量・単位・番号を入力して確認後に提出する。
6. お知らせで未送信、確認待ち、差戻し、管理側の対応を確認する。差戻し時は対象便で修正理由を添えて再提出する。
7. 結果確認中は「処理結果を照会」。自動再送は行わない。未処理と確認できた場合だけ同じ操作IDで明示再送する。
