## 確認した既存資産と制約

- `app/deploy/dgx/compose.yml`：PostgreSQL/API/Nginxの非公開検証構成。Tailscaleアドレスの8101に固定された設定。稼働確認は未実施。
- `app/deploy/dgx/README.md`：既存認証はvalidation-only。本番認証相当の確認にはならない。
- `deploy/life-id/`：既存デモ用。currentおよび固定リリースv1～v4を今回の構築で上書きしない。
- `app/server/index.mjs`：共通PG API。DB名を `ecodump_direct_validation` に制限している。別環境化は独立PGインスタンス/ボリュームを使用するか、環境ガードを明示的に設計する必要がある。単に本番・開発DBへ接続先を変えない。
- `app/server/setup.mjs`：Mac専用のローカルPG起動処理を含む。サーバー用マイグレーション・seed手順としてそのまま実行できる前提にしない。
- `app/vite.config.mjs`：複数APIの開発用proxyが存在する。ステージングでは共通PGの `/api/direct` と `/api/match` を同一の接続先へ向け、旧SQLiteで成功を代替しない。
- 共通IDと未対応操作の現状は `COMMON_LOCATION.md` を参照。成田seed/ID manifestの存在は未確認。

## 環境構成案

施工・受入・ドライバーの既存UI → 同一オリジンのAPI → ステージング専用PostgreSQL。

- 開発・既存デモと独立したサービス名、公開ポート、ボリューム、認証情報、添付保存領域を用意する。
- スマートフォンから撮影・位置取得を確認する共有環境では、端末から到達できるHTTPSを整える。localhostでの模擬確認を代用しない。
- 元のUI・機能と承認済みナビゲーションは維持する。ステージング表示を加え、匿名プレビューと実保存を区別する。
- 施工・栃木受入・茨城受入・ドライバー各人を別アカウントでログインする。役割パラメータで権限を付与しない。
- 検証データのみを使用し、外部メール/Push/決済は初期検証の対象外。送信したように見せない。
- テスト対象のソース版、マイグレーション版、seed版、デプロイ日時を記録する。共有作業ツリーを一括コミットしない。

## テスト順と合格条件

|順番|対象|合格条件|
|---|---|---|
|1|環境|3画面が専用API/DBに接続し、別アカウントで認証できる|
|2|基本の1便|予約→受入承認→配車→運行報告→入退場→伝票→数量確認が同じ運行に残る|
|3|保存・証拠|再ログイン/再取得後も9.5m³と原票が一致。未確認数量は別枠|
|4|複数便・行先|同車3便、A/B工区、栃木/茨城を混同せず集計|
|5|権限|他受入先、担当外現場、他ドライバーのAPI/画像取得と更新を拒否|
|6|例外|変更・取消・代車・遅延・受入不可・訂正の権限と履歴を確認。未実装は未合格|
|7|通信・競合|二重操作、古い版、応答喪失でも重複せず、結果照会で回復|
|8|マッチング|検索→条件確認→予約。マッチ成立だけでは予約/配車を確定しない|
|9|実機|iPhone/Android等で写真、通信断、位置権限、ロック復帰を確認|

API・DBテスト、ブラウザテスト、実機テストの証跡を分ける。カメラ/OCR/GPS/ETCの模擬結果を実接続合格に含めない。
