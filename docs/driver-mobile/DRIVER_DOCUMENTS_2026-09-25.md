2026-09-25 / ローカル・隔離検証のみ。本番公開なし。

## 参照と判断の区別

- 議事録 `ECO_DUMP_画面要件詳細議事録_2026-09-25.pdf` 12〜14ページを本文抽出・レンダリングの両方で確認。資料は「検討用 v1.0 / 正式承認前」であり、全記載を確定仕様と扱っていない。
- IMG_4506〜4512 を画像で確認。4507の「ドライバー伝票 写真 読み込み機能」を対象要求として採用。他画面のメニュー・マッチング再編は今回変更しない。
- 今回ユーザーが明示した「写真＋手入力＋管理者確認」「原票単位の保存」「提出と実績確定の分離」を実装対象とした。
- 原票の補足項目・番号なし理由入力は今回の設計提案。総重量・空車重量・正味重量は単位込みの原文入力で保存し、自動計算しない。
- 正式な確認担当・実績訂正権限、入退場の確定者、原票番号なし運用、単位換算、電子署名、GPS運用は未決。既存隔離環境の `has_scope(...,'receiving')` による受入担当の確認・差戻し・明示的実績確定を利用し、新たな本番権限は付与していない。

|追加|原票撮影選択、手入力、確認、提出、差戻し再提出|運行から操作、写真＋入力を原子的に保存、履歴に原本を残す|
|接続|受入側の伝票確認・差戻し|並行作業で追加された `direct.receipts / receipt_history / receive_mutate / ReceiptEvidence` を利用。別伝票DBは作成しない|

他作業者による未コミット変更が多数あるため、全体置換・リセット・コミットをしていない。共通ファイルへの変更は接続点と表示箇所に限定。並行追加された受入伝票インポートとの重複は解消した。

## データと保存

- 既存：bookings → trips → trip_events / attachments / receipts / receipt_history / actuals。
- 追加：`direct.driver_document_fields`。添付ID、予約ID、原票日付・番号/番号なし理由・品名・車番・搬出元/受入先・計量票記載・本人照合を、提出時の不変レコードとして保存。
- `POST /api/direct/driver-document-submit`：担当ドライバー限定。原本添付・確認待ち伝票・入力項目・操作結果を同一トランザクションで保存。初回または差戻しからの提出のみ。
- `GET /api/direct/driver-document-fields?bookingId=...`：DB RLSで取引当事者と担当者に限定。
- `GET /api/direct/driver-identity`：本人の所属と本人割当車両の車番。
- `GET /api/direct/operations/:key`：既存の処理結果照会。二重送信は同じ操作ID・同じ内容で同じ結果。別内容の操作ID再利用は拒否。
- 写真は既存制限に合わせJPEG/PNG、2MB以下。選択したファイルを再圧縮・変換せず保存。元の写真は再提出後も既存添付と履歴から参照可能。
- 端末：IndexedDB `ecodump-driver-documents-v1`、ユーザーID＋運行IDをキーに写真・入力・操作IDを保存。送信中/未送信/失敗/結果確認中/送信済みを分離。結果不明時は入力を固定し、自動再送しない。
- 下書きはブラウザ領域に残る。ログアウトで消去しない。他ユーザーは別キー。ブラウザのデータ削除・容量不足・OSのストレージ消去まで保証するものではない。完全オフラインでのアプリ初回起動・再起動用Service Workerは未実装。
- t/m³は原票単位を保持。予定がm³で伝票がtでも自動換算しない。数量精度は既存DBの小数3桁。

## 状態・権限

運行：配車済み → 現場到着 → 積込完了・出発 → 受入先到着 → 荷下ろし完了。到着/荷下ろし報告は入場/退場記録を生成しない。

伝票：未提出 → 確認待ち → 差戻し → 修正再提出 → 確認待ち。受入側は原票を照合し、荷下ろし完了後に別の明示操作で実績確定する。伝票提出・ドライバー報告から実績を自動確定しない。既存受入APIの「receipt_confirm」は実績確定を含むため、そのボタンには実績確定を明記している。

運行訂正権限の新設はしていない。誤報告・割当違いは次操作を止めて担当者へ確認する案内を置いた。アプリ内の問い合わせ送信は未接続。

## 検証結果

### 隔離環境・実API/DB

`node --test app/server/tests/integration.test.mjs app/server/tests/driver-documents.test.mjs`：14テスト成功。追加テストは下記を一連で検証。

- 施工予約 → 受入確認 → 割当 → 4報告 → 受入実績確定の既存フロー。
- 原本のバイト一致、原票項目・t単位保持、提出時はactualがnull。
- 別ドライバー・他社・担当外受入・施工側からのドライバー提出拒否。
- 写真の権限外取得404、入力項目の権限外取得空、DBロールでのRLS拒否。
- 同一操作IDの同時送信と再送が重複しない。異なる内容の同一ID409、古い版の再提出409。
- 差戻し理由 → 修正再提出 → 旧写真・旧値・新値の履歴。
- DBコミット後の接続切断 → 操作結果照会 → 同じID再送でも履歴・写真が増えない。
- 再認証後も同じ提出内容取得。受入側による明示確定後、3役割で同じ数量を取得。
- 提出後に受入実績を自動確定しない。受入担当以外の確定403。

### ローカルブラウザ

Codexブラウザの390×844幅（iPhone風筐体）で確認。実機Safari検証ではない。

- 本人所属・車番・当日割当、次の運行、状態報告確認ダイアログ、現場到着の実保存。
- 匿名のテスト伝票PNGをファイル選択、数量7.250・単位tを入力、再読み込み後に写真/入力を復元、提出前確認、保存・再取得表示。
- 受入側別セッションで同じ写真/入力を取得、差戻し理由を保存、ドライバー再取得で反映。
- 専用ローカル障害プロキシ5206でAPI通信を切断。写真・入力を保持し「結果確認中」、復帰後再読み込み→未処理照会→同一IDで明示再送。
- 同プロキシでDB保存後のHTTP応答だけ破棄。「結果確認中」から照会により「送信済み・DB再取得確認済み」へ復旧。
- ログアウト→再ログイン後も提出済み伝票と報告を表示。
- 通常プレビュー5202に障害設定は適用していない。

## 試用手順と残事項

1. `http://127.0.0.1:5202/?data=isolated&role=driver`。隔離アカウントでログイン。会社・氏名・車番を確認し次の運行を開く。
2. 停車中に次の大きい報告ボタン→確認→保存。伝票リンクから写真、原票項目、数量/単位を入力。確認チェック→提出前確認→提出。
3. 受入側は同じ予約の伝票・数量確認で写真と値を照合。問題があれば理由付き差戻し。ドライバーは再取得し、修正理由を付けて再提出。
4. 結果確認中は再送せず照会。未処理が確認された場合だけ同一IDで再送。荷下ろし完了後、受入担当が実績を明示確定。
5. 既存の地図・問題報告試作は `?app=driver` 側に残っており別データ。実API接続済みと混同しない。

優先P1：実機撮影（2MB上限・HEIC対応）、本番の確認/訂正権限決定、原票番号なし運用、画像保存期間/端末保護/容量、長期オフライン起動、複数原票/便の業務ルール。
優先P2：OCRプロバイダ接続と候補確認、業務経路/GPS/Push、問い合わせ・運行訂正・問題報告API。実サービス契約や位置共有範囲は今回決めていない。
