# 共通API・DB：直接運搬の実装・検証引き継ぎ

2026-09-25。対象は発生土マッチを経由しない1件の運搬。本番データ・本番認証・公開環境は使用していない。

## 完成した範囲

施工側の搬出予定・直接予約 → 受入側の条件確認・予約確定 → 施工側の車両・ドライバー割当 → 担当ドライバーの4段階報告 → 受入側の数量確定 → 双方の実績表示を、同じPostgreSQLへ保存する。

- 施工側：http://127.0.0.1:5202/?data=isolated&role=construction
- 受入側：http://127.0.0.1:5202/?data=isolated&role=receiving
- ドライバー：http://127.0.0.1:5202/?data=isolated&role=driver

ログイン済みのプレビューを起動済み。検証専用アカウントは `app/server/.local/credentials.json`（Git対象外・0600）。認証情報を資料に転記しない。

## 既存との区別

既存のReact/Vite、ECO DUMPロゴ・緑/ライムの配色、ドライバーのiPhone枠・下部メニュー、会社/プロフィール/所属/現場/車両/ドライバーの基本構造を活用した。既存のSupabase設定・Auth・リポジトリ・schema.sqlを確認したが、この環境には接続設定がない。元のschema.sqlはPostGISを含むため、そのまま隔離DBへ適用したとは扱わない。

今回の接続画面は `src/integration/`、APIは `server/index.mjs`、DBは `server/migrations/001_core.sql`〜`005_audit_scope.sql`。既存管理画面・端末内試作の機能を削除せず、`data=isolated` で実保存の経路を分けている。旧試作のデータは自動移行していない。並行作業のmatching/workflow/receiving実装と追加マイグレーションは保持した。その全機能が本報告のテストに含まれるわけではない。

認証は隔離環境専用の実パスワード認証（scrypt、ハッシュ化したセッショントークン、有効期限8時間）。本番Supabase Authの接続検証ではない。APIの接続ロールと認証用ロールを分離し、リクエスト単位のユーザーIDをDBトランザクションに設定する。

## データ・権限・状態

会社 → 所属ユーザー/役割 → 担当現場・受入場所のscope。予約が搬出現場・受入場所・双方の会社を結び、予約 → 便 → 車両/ドライバー → 状態報告 → 確定実績を関連付ける。添付書類は予約・便・登録者に関連する。変更操作は監査履歴と操作結果を同一トランザクションで保存する。

|操作|API/DBで必要な権限・条件|
|---|---|
|予約作成|有効な施工所属・自社担当現場・登録済み取引先受入場所|
|予約確定|有効な受入所属・担当受入場所・申請中・条件同意|
|配車|施工担当範囲・確定予約・自社の有効車両/ドライバー・時間重複なし|
|状態報告|本人に割当済みの便・順序/時刻/版の一致|
|実績確定|受入担当範囲・荷下ろし済み・単位一致・差異理由|
|添付取得|当該取引の担当管理者または担当ドライバー|

DBのRLSとSECURITY DEFINERの限定更新関数で検証し、通常APIロールへ直接テーブル更新権限を与えていない。ドライバーには契約条件本文・管理用監査記録を開示せず、担当便に必要な投影を返す。会社全体への無制限共有は行わない。所属失効は既存セッションにも反映する。

条件合意 `pending/agreed`、予約 `requested/confirmed`、運行 `assigned → site_arrived → in_transit → receiver_arrived → unloaded`、実績 `未作成/confirmed` を別に管理する。直接予約の確定操作では条件同意と予約確定を同一トランザクションで記録するが、状態項目は分離している。荷下ろし報告だけでは実績は確定しない。

今回の最小単位は1予約=1便。複数往復は別予約・別便IDと車両日別往復番号で区別する。1予約を複数便へ展開する機能は未実装。

## APIと整合性

共通接頭辞 `/api/direct`：

|API|用途|
|---|---|
|POST /session|検証アカウント認証|
|GET /context|本人・役割・担当範囲・利用可能な現場/車両/ドライバー|
|GET /bookings|権限内の予約・便・報告・実績・添付一覧|
|POST /actions/create, confirm, assign, report, actual, attachment|作成・確定・配車・報告・実績・添付保存|
|GET /operations/:key|本人の更新処理結果照会|
|GET /attachments/:id|権限を再検証した実ファイル取得|

更新にUUIDのIdempotency-Key、更新対象のexpectedVersionを要求。同一キー/同一内容は保存済み結果を返し、別内容は409。行ロック・操作キーロック・一意制約により並行二重登録と古い版を拒否。受入容量・車両/ドライバー重複もロック下で確認する。操作結果は期限削除せず保持する。

送信前に操作キーをsessionStorageへ記録。通信中、送信失敗、結果確認中、未適用、送信済みを区別する。不明な結果を自動再送せず、照会で確定済みなら再取得し、未適用が確認されたときだけ同じキーで明示再送する。保存成功はサーバーの応答と再取得を確認して表示する。

## 再開手順・運用境界

プロジェクトルートで `node app/server/setup.mjs`、`node app/server/index.mjs`。別ターミナルのappディレクトリで `npm run dev -- --config vite.integration.config.mjs`。テストはルートで `node --test app/server/tests/integration.test.mjs`。

PostgreSQL16の専用クラスタは `app/server/.local/postgres`、DB名 `ecodump_direct_validation`。DBはTCP非公開のUnix socket、APIは127.0.0.1:6102、画面は127.0.0.1:5202。DB・資格情報はGit対象外。setupは既存データを消さず、適用済みマイグレーションのSHA-256を検証する。適用済みSQLを編集せず追加マイグレーションで変更する。共有のsetup適用一覧を編集するときは、他作業の登録も保持すること。
