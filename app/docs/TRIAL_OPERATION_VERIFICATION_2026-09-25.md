## 4. 今回修正した問題

1. ローカルUIのポートが固定許可リスト外だと隔離PostgreSQLのログインが403になる問題を修正。APIは引き続き127.0.0.1／localhostだけにバインドする。
2. PC上部、ページヘッダー、絞り込み、一覧操作の一部が38px以下だったため、頻用操作を44px以上へ統一。
3. 予約変更、取消、配車変更、遅延、受入不可、数量訂正の隔離API処理と監査履歴を追加。
4. 同じ予約の複数便を便番号・別trip IDとして返し、画面にも複数便を表示。
5. 受入不可／取消後にドライバーが状態報告できる抜けを拒否。
6. 数量訂正を上書きだけにせず、変更前・変更後・理由・担当者・日時を履歴保存。
7. 発生土マッチの画面試験を現行ログイン・案件フォーム・条件提示フローへ更新。画面遷移前に保存応答を待ち、結果不明を作らないようにした。

## 5. 残課題と優先度

### P0 — 試験運用開始前

1. **共通APIの一本化**: 現在、主要な永続連携は隔離PostgreSQL、今回の例外系は補助SQLite APIでも検証している。試験運用では予約変更・取消・遅延・数量訂正をPostgreSQL側の同一API・同一監査ログへ統合する。
2. **実機・実通信確認**: iPhone／Android実機でGPS権限、圏外→復帰、バックグラウンド、端末時刻差、Push通知を確認する。
3. **環境設定**: 本番用認証、秘密情報、通知送信元、添付ストレージ、地図／道路規制API、監視・バックアップを確定する。

### P1 — 限定運用前または初回週

1. 予約・運行・実績の運用者向け監査ログ閲覧画面。
2. 例外状態の通知先、エスカレーション時間、受入不可時の代替受入先ルール。
3. テストデータ初期化、検証会社追加、利用停止・退職者セッション失効の運用手順。
4. 数量訂正の承認者分離と帳票再発行ルール。

### P2 — 本番導入前

1. WCAGコントラストの自動計測とスクリーンリーダー実機確認。
2. 大量データ、長時間稼働、添付上限、ログ保管期間の性能試験。
3. CarPlay／Android Autoは別ネイティブ審査・実機工程として扱う。

## 6. 試験運用手順

1. 隔離環境を初期化し、匿名の施工会社・受入会社・運送会社・車両・ドライバーを登録する。
2. 施工側で直接予約を1件作成し、操作ID・予約ID・versionを記録する。
3. 受入側で内容を再取得し、受入確定する。別ブラウザで反映を確認する。
4. 施工側で車両・ドライバー・便番号を割り当てる。同じ車両の2便目は別便番号で作成する。
5. ドライバー端末で自分の便だけが見えることを確認し、到着→出発→荷下ろし完了を順番に報告する。
6. 受入側で実績数量を確定し、施工側・受入側双方で再取得する。
7. 別予約で変更、取消、配車変更、遅延、受入不可、数量訂正を1件ずつ実行する。
8. 同一操作の二重送信、古いversion、応答切断を試し、重複せず結果照会できることを確認する。
9. 権限外会社・別ドライバーでURL直入力とAPI更新を行い、非表示／403を確認する。
10. ログアウト・再ログイン、API再起動後も保存内容が維持されることを確認する。
11. 問題が出た場合、操作ID、予約ID、便ID、ユーザー、時刻、画面、通信状態を記録し、同じ更新を新しい操作IDで再送しない。

## 7. 簡易操作説明

### 施工側

1. 「搬出管理〈ホーム〉」で日付・現場・受入先・状態を絞り込む。
2. 既存取引先なら「搬出予定・搬入予約をDBへ登録」、新規候補なら「発生土マッチ」を使用する。
3. 受入確定後、「配車・運行管理」で車両・ドライバー・便番号を割り当てる。
4. 運行開始前だけ予約・配車を変更できる。相手確認が必要な変更は予約確認待ちへ戻る。
5. 「実績・帳票」で受入確定数量を確認する。

### 受入側

1. 「搬入予約・受付」で申請中予約を確認する。
2. 条件を満たす場合は予約確定、満たさない場合は理由を付けて受入不可を報告する。
3. 荷下ろし完了後に実績数量を確認・確定する。
4. 訂正時は計量票を再確認し、数量と理由を記録する。

### ドライバー

1. 「今日の運行」で自分に割り当てられた便を確認する。
2. 便番号、現場、受入場所を確認し、到着→出発→荷下ろし完了の順に報告する。
3. 遅延時は工程を進めず、「遅延を報告」で理由と到着見込みを送る。
4. 結果不明表示になった場合は連打・再送せず、処理結果照会を行う。
5. 荷下ろし完了は受入実績確定ではない。数量確定は受入側が行う。
